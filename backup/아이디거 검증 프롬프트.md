## 1단계: 너가 직접 조사

다음을 코드/git/라이브 URL에서 직접 확인하고 요약 보고:

- **기본 정보**: 시작일, 커밋 수, 최근 30일 커밋 빈도, 기술 스택
- **작동하는 기능**: 라우트/엔드포인트/페이지에서 실제로 동작하는 핵심 흐름
- **포기/미완성 흔적**: TODO/FIXME, 주석 처리된 큰 블록, `_old/` `_draft/` 등
- **외부 데이터/API 검증 (가장 중요)**: 코드에서 쓰는 외부 API/데이터 소스를 식별하고, 환경변수로 실제 호출해서 응답·품질·약관 확인. 비전을 뒷받침할 만큼 충분한가?
- **측정 인프라**: 분석(GA/Plausible/PostHog 등) / 결제(Stripe/Toss 등) / 인터뷰·waitlist 도구 통합 여부
- **라이브 URL** (README/env에서 찾을 수 있으면): 핵심 사용자 흐름 직접 시도

조사 결과를 한 화면으로 요약 출력하고 2단계로 넘어가.

## 2단계: 나에게 묻기 (코드에 없는 것만)

다음 4가지를 질문해. 내가 답할 때까지 3단계로 넘어가지 마.

1. **원래 가설**: 시작할 때 누가, 왜, 얼마를 낼 거라 믿었는가?
2. **외부 수요 신호**: waitlist 수, 인터뷰한 사람과 반응, 결제 의향 표명, 자발적 입소문 등 (없으면 "없음")
3. **가장 불안한 부분**: 직감적으로 가장 걱정되는 한 가지
4. **대안**: 이 프로젝트를 중단하면 그 시간으로 무엇을 할 것인가

## 3단계: 판단

1단계 조사와 2단계 답변을 종합해서 결론. 다음 원칙을 엄격히 따를 것:

- **코드가 사용자 주장과 충돌하면 코드를 믿는다.** 예: 사용자가 "수요 있다"는데 측정 인프라가 없다 → 검증 불가로 처리
- **외부 데이터/API가 비전에 부족하면 그것만으로 KILL.** (whereirank.net 교훈: 데이터 없으면 비전 불가능)
- **가장 가혹한 외부 비판자의 시각으로 평가.** 균형 잡힌 시각 금지. kill 사유 3개를 먼저 나열하고 사용자가 반박 가능한지 보라
- **매몰비용 무력화**: "오늘 0시간 투입했다 가정하고, 이 상태(작동 기능 + 측정 결과 + 데이터 검증 + 남은 작업량)를 처음 보는 외부 1인 개발자라면 이 프로젝트를 인수하겠는가?" 라는 질문에 답하라
- **결론은 셋 중 하나로 명확히.** "조금 더 해보자", "두 가지 동시에" 같은 회피 답변 금지
